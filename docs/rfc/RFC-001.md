# Adaptive Retrieval Core

## 需求与架构基线（RFC-001）

**副标题：** Benchmark-driven Retrieval Subsystem for Enterprise AI Harnesses  
**版本：** v0.1 · 首版冻结（FROZEN）  
**冻结日期：** 2026-11-05  
**文档类型：** Requirements & Architecture Baseline / Request for Comments  
**适用阶段：** V0 立项与设计；V1、V2 作为扩展约束  
**主文档：** 本 Markdown 文件为规范原件；DOCX 为阅读副本

> **一句话定义**：建立一个独立于 RAG 和 Agent 框架的检索核心，通过稳定的数据与执行契约，支持可替换的检索策略、不同业务的数据适配和可复现的离线评价，并以算法实习作品集为主要交付目标。

---

## 0. 冻结决定与修订依据

本文档固定**项目目标、能力边界、核心数据契约、验证方式与阶段验收原则**；不冻结具体模型、最终搜索后端、超参数、代码目录或服务部署形态。这些属于后续详细设计与实验决策。

相较 Day 2 第 1 讲讨论草案，进行了五项实质性修订：

| ID | 修订 | 原因与结果 |
|---|---|---|
| R-01 | 分开技术文档的**全库检索**与商品的**给定候选重排** | 这两类 Benchmark 不能互相代替。V0 只证明同一个检索核心能支持两种任务协议；完整商品检索留给 V1 专项验证。 |
| R-02 | 将 Evaluation 从线上搜索 API 中分离 | 线上只暴露稳定检索契约；离线评测复用相同执行核心，但拥有独立数据、配置及输出流程。 |
| R-03 | 明确 Entity / Unit / Index Snapshot 关系 | 防止切分变化、重建索引与旧版本内容造成 ID 错配、脏结果和评价不可复现。 |
| R-04 | 收紧“企业级安全”主张 | V0 只运行公开/授权测试数据；字段预留不代表已实现真实 ACL，未验证前不得声称支持企业私有数据隔离。 |
| R-05 | 验收拆分为功能、质量、成本与可复现性 | 不能以“接入了新模型”替代真实的算法收益或可靠性验证。 |

### 0.1 不变的设计原则

1. **算法与 Harness 并重**：检索质量、实验可信度与接口可复用性同等重要。
2. **成熟基线优先**：先比较 BM25、Dense、Hybrid、Cross-Encoder，再根据错误归因增加复杂能力。
3. **业务语义不被通用性抹除**：共享 Core，不强求技术文档和商品具有相同相关性与数据粒度。
4. **评测先行**：每项算法增强应对应可验证的质量、成本或可靠性假设。
5. **有限抽象**：只为已经明确的两个场景和一个未来的多模态扩展点设计接口。

## 1. 项目目标与明确非目标

### 1.1 成功标准

- **算法**：实现可复现的 BM25、Dense、Hybrid（RRF）和 Cross-Encoder 分阶段方案；报告与单模块基线的对照、消融、失败案例及质量-延迟权衡。
- **工程**：支持统一 `search()` 接口、两个业务适配器、数据版本及索引快照、执行 Trace、基础元数据硬过滤和可配置检索策略。
- **证据**：在公开 Benchmark 上提供规范的指标、实验配置、硬件条件、检索结果文件与复现说明；实测结果决定是否继续优化，而非事先承诺超越 SOTA。
- **交付**：独立运行的 Python 核心和最薄的调用示例；是否提供 HTTP 适配器由实际集成需求决定。

### 1.2 明确不属于 V0 的目标

- 通用 Agent Runtime、Agentic Search 决策闭环或完整 RAG 生成系统。
- 自研 HNSW、ANN 引擎、倒排索引或分布式搜索内核。
- 同时兼容多个搜索后端、复杂插件商店或无限策略 DSL。
- 训练新的基础 Embedding 模型、复杂 Learning-to-Rank 模型或自主路由器。
- 多租户生产级 ACL、身份认证、完整高可用集群与实时流式更新。
- V0 实现图像索引与跨模态相似度检索；仅避免在数据模型中封死这种可能性。
- 在缺乏用户行为与业务数据时声称完成个性化推荐或商业转化优化。

## 2. 业务范围与需求矩阵

### 2.1 业务 A：技术文档检索（V0 主路径）

**用户意图**：查技术细节、报错信息、API 版本、概念解释和专业证据。  
**检索对象**：原始技术文档（Entity）；文档片段、章节或代码块（Unit）。  
**主要要求**：精确术语与语义召回、定位来源、版本过滤、按文档聚合、可追溯证据。  
**最终输出**：命中 Unit，同时能还原文档 Entity、来源位置与修订版本。  
**首要评测**：全库检索；优先 BEIR / SciFact 等已有标准 Qrels 的数据。

### 2.2 业务 B：商品内容搜索（V0 第二路径）

**用户意图**：搜索商品名称、用途、属性组合及自然语言需求。  
**检索对象**：商品（Entity）；标题、描述、属性文本等（Unit）。  
**主要要求**：结构化属性、字段过滤、商品级排序，以及 Exact / Substitute / Complement / Irrelevant 的业务区分。  
**最终输出**：商品 Entity；可附带触发匹配的 Unit / 字段证据。  
**首要评测**：Amazon ESCI Task 1 的**给定候选集重排**，不把它冒充为商品全库召回。商品全库检索若追加自建任务，必须单独说明 Qrels 覆盖与评价局限。

### 2.3 需求优先级

| 能力 | V0 | V1 | V2 |
|---|---|---|---|
| 单一统一检索核心、SearchRequest/Hit/Trace | 必须 | 维持 | 维持 |
| BM25、Dense、Hybrid/RRF、Cross-Encoder | 必须 | 优化 | 按需升级 |
| 技术文档全库检索 + 文档级 Benchmark | 必须 | 扩充 | 维持 |
| 商品给定候选重排 + ESCI Benchmark | 必须 | 扩充 | 维持 |
| 技术文档与商品 Schema 适配 | 必须 | 强化 | 维持 |
| 元数据硬过滤、版本/字段一致性 | 基础必须 | 完整验证 | 维持 |
| 完整的 Entity/Unit 聚合、更新和删除 | 最小一致性检查 | 完善 | 维持 |
| 商品全库检索与独立标注协议 | 不宣称完成 | 计划验证 | 可扩充 |
| 授权隔离与私有企业语料 | 不支持；公开测试语料 | 独立安全验收 | 按需 |
| Query-aware 自适应路由 | 不要求 | 视消融收益 | 可选 |
| 图文多模态 | 预留非阻断性扩展点 | 视资源准备 | 目标扩展 |

## 3. 系统边界与执行架构

### 3.1 责任划分

```text
调用方：业务搜索 UI / RAG / Agent / 其他 Harness
           │ 结构化 SearchRequest
           ▼
     Retrieval Core ─────────────► SearchResponse + Trace
       ├─ Query & Validated Filters
       ├─ Sparse / Dense Retrievers
       ├─ Fusion (RRF) & Reranker
       └─ Result Assembly (Unit ↔ Entity)
           │
           ▼
      单一搜索后端 + 索引快照

离线：Benchmark Runner ──复用同一检索核心──► Runfile / Metrics / Report
数据：Domain Adapter ─► Entity / Unit ─► Index Builder ─► Index Snapshot
```

### 3.2 边界决定（ADR）

| 决策 | 内容 | 取舍 |
|---|---|---|
| ADR-01 | 单个 Retrieval Core，不依赖具体 RAG / Agent Framework | 减少与上层应用耦合；不提供 Agent 工具规划。 |
| ADR-02 | 以 Python `search()` 为稳定接口；HTTP 是薄适配层 | 优先实现算法与测试，不提前展开微服务架构。 |
| ADR-03 | 评测通过离线 Runner/CLI 复用 Core | 避免线上请求调用评测逻辑；确保对比与部署算法路径一致。 |
| ADR-04 | V0 选择**一个**主搜索后端；候选 OpenSearch，完成小规模技术验证后确认 | 不提前抽象多后端；避免未经测试锁定具体集成版本。 |
| ADR-05 | Query Strategy 可配置，但只暴露少量经过验证的预设组合 | 不设计通用编程语言或任意 DAG 工作流。 |
| ADR-06 | Trace 的内部阶段信息与公开响应字段分离 | 支持性能和错误归因；避免暴露敏感内容与未经校准的分数。 |

> **架构性质说明**：本项目在 V0 追求“企业级设计约束下的可复现实验原型”，不以未经安全、容量和可用性验收的实现宣称生产就绪。

## 4. 数据契约（Conceptual Contract）

### 4.1 Entity — 最终业务对象

| 属性 | 含义 | 约束 |
|---|---|---|
| `domain` | `technical` / `product` | 必填，参与 ID 命名空间 |
| `entity_id` | 业务稳定 ID | 必填，不随索引重建变化 |
| `revision` | 业务内容修订 | 必填，同一修订视为不可变输入 |
| `title` | 文档或商品标题 | 必填或由适配器明确缺省策略 |
| `source_ref` | 源数据及可追溯信息 | 必填，不保证公网 URL |
| `metadata` | 经过业务 Schema 校验的字段 | 必填但允许空对象 |
| `visibility_ref` | 将来授权策略所需的关联引用 | 预留字段，V0 不等于 ACL 实现 |

逻辑唯一键：`(domain, entity_id, revision)`。商品变体 / SKU 作为商品 Schema 的关系，不在 V0 强制上升为通用层级。

### 4.2 RetrievalUnit — 实际参与检索的单元

| 属性 | 含义 | 约束 |
|---|---|---|
| `unit_id` | 检索单元 ID | 在给定源修订、分块策略版本下稳定 |
| `entity_key` | Entity 的完整逻辑键 | 必填；防止新旧修订混用 |
| `unit_type` | `passage` / `field_text` / `code` 等 | 可扩展枚举，V0 文本有效 |
| `text` | 文本索引内容 | V0 必填，允许多字段规范化 |
| `location` | 章节、偏移或字段路径 | 必填，支持定位与去重 |
| `chunker_version` | 切分策略签名 | 可由快照 Manifest 继承 |
| `content_hash` | 单元内容指纹 | 用于一致性检查和重建审计 |

一个 Entity 可对应多个 Unit。一个 Unit 可以被多种索引策略表示；Embedding 不是 Entity 的语义身份，不应写成业务稳定字段。

### 4.3 IndexSnapshot — 索引版本与一致性

最小 Manifest：`snapshot_id`、`dataset_fingerprint`、`entity_revision_set` 或批次引用、`chunker_config_hash`、`encoder_id/version`、`index_backend/version`、`created_at`、`status`。

冻结规则：**评测在一个固定数据快照和索引快照上运行**。查询期间不得混用旧 Unit 与新 Entity 修订；重建失败时旧快照应保持可用，或明确让测试失败，而非静默返回脏数据。

V0 可通过全量重建与快照切换满足该原则，不要求实现实时增量索引流水线。

### 4.4 示例：概念映射（非最终 SDK 结构）

```json
{
  "entity": {
    "domain": "technical",
    "entity_id": "pytorch-adamw-doc",
    "revision": "r1",
    "title": "AdamW documentation",
    "source_ref": "dataset://tech/pytorch-adamw-doc/r1",
    "metadata": {"library": "pytorch", "version": "2.9"}
  },
  "unit": {
    "unit_id": "u-doc-r1-section-03",
    "entity_key": ["technical", "pytorch-adamw-doc", "r1"],
    "unit_type": "passage",
    "location": "section:03",
    "text": "Illustrative excerpt for data contract only"
  }
}
```

以上仅为虚构的字段示例，不代表所引用文档真实文本或内容来源已被导入。

## 5. 搜索契约与执行不变量

### 5.1 SearchRequest（逻辑字段）

- `query`：查询文本，不能为空。
- `domain`：业务类型；不可跨业务意外混检。
- `top_k`：最终返回数量；具有上限。
- `filters`：Schema 校验后的**用户业务过滤**，非法字段拒绝，硬约束不进入软排序权重。
- `strategy_id`：枚举式配置，初期为 `bm25` / `dense` / `hybrid` / `hybrid_rerank`。
- `return_level`：`unit` 或 `entity`；默认由 Domain Profile 定义。
- `trace_level`：控制可返回的诊断摘要，不等于完整内部日志访问权限。

将来如需 ACL，身份信息必须来自可信上下文，服务端强制过滤，**不可让客户端任意声明自身权限**。

### 5.2 SearchResponse / SearchHit（逻辑字段）

- `hits[]`：`entity_key`、可选 `unit_id`、`rank`、`score`、`score_type`、允许返回的内容与定位、Schema 校验后的业务字段。
- `snapshot_id`、`strategy_id`、`trace_id`、请求耗时和状态（成功 / 部分失败 / 失败）。
- 内部 Trace：各路候选数、去重后数量、阶段耗时、候选 ID/排名、模型和配置版本及必要错误信息。

**重要不变量：** BM25、Dense、RRF、Cross-Encoder 的原始分数不具备天然统一尺度。`score` 必须能标识评分阶段与类型，跨策略比较质量使用统一 Benchmark，而不是直接比较分数大小。

### 5.3 过滤、聚合与失败规则

1. 硬过滤必须在候选选择时得到保证；不允许用低分惩罚来近似业务硬条件。
2. `return_level=entity` 时，应显式规定 Unit 到 Entity 的聚合方式、同一 Entity 去重方式以及最终返回数的含义。
3. 某一检索分支超时或失败，应记录状态；是否回退到 BM25 等安全策略由明示策略控制，不能在离线 Benchmark 中静默更换实验条件。
4. 无结果、无效过滤、不存在的索引快照、模型版本不一致必须有可测试的行为。
5. V0 仅处理公开或有明确使用授权的数据；私有数据隔离和完整 ACL 不在验证范围内。

## 6. 算法基线与策略空间

### 6.1 固定最小策略集

| Strategy | 召回 | 融合 | 精排 | 作用 |
|---|---|---|---|---|
| `bm25` | Sparse | — | — | 词项精确匹配基线 |
| `dense` | Embedding + ANN/Exact | — | — | 语义检索基线 |
| `hybrid` | BM25 + Dense | RRF | — | 多通道融合基线 |
| `hybrid_rerank` | BM25 + Dense | RRF | Cross-Encoder | 分阶段精排基线 |

候选数、RRF 常数、Embedding/Reranker 型号、ANN 参数及后端由配置管理；以上策略应支持公平固定参数和一致快照比较。

### 6.2 暂不冻结的技术选型

- Embedding 与 Reranker 模型具体名称、量化方案及是否微调。
- 检索后端最终选型、机器规格与目标 QPS。
- 文档切分长度、重叠率和 Unit→Entity 聚合函数。
- 是否增加 Query-aware 路由、ColBERT、图文联合编码。

只有当实验说明必要性时，才提交新的设计决策（ADR）引入以上能力。

## 7. Benchmark 契约与评价边界

### 7.1 两种不同任务，不得混报

| 协议 | 输入 | 评价对象 | V0 数据选择 |
|---|---|---|---|
| **Full-corpus Retrieval** | 完整语料、Query、Qrels | 检索器生成的全库排名 | BEIR SciFact，必要时补充第二个文本领域 |
| **Candidate Reranking** | Query、固定候选列表及标签 | 仅在给定候选中的排序 | Amazon ESCI Task 1，先固定一种 Locale |

对于商品的 `Candidate Reranking`，BM25/Dense/Hybrid 也必须在同一固定候选集合内评价；不得与未受同一候选限制的全库结果混排。对于技术文档的 Passage 检索，应先用预先规定的策略聚合为文档级，再与文档级 Qrels 比较。

### 7.2 Qrels 与数据切分

- `Qrels`（查询-检索对象相关性标注）应声明对象粒度、等级、来源及未标注项处理规则。
- 公开 Qrels 可能不完备。报告按官方评价约定计算的数值，同时披露标注局限；不把未标注结果直接宣称为真实无关。
- **开发、调参、测试必须隔离**。BEIR 等没有适合当前用途的验证集时，指定独立调参集或训练数据划分；最终测试集不用于反复调参。
- ESCI 先固定一种 `product_locale`，保留数据源原始 `split`，训练分割后的调参集必须按 Query 分组切分以避免同 Query 泄漏；ESCI 的 E/S/C/I 与 NDCG gain 映射要在实验前锁定并记录。
- 明确查询子集、数据条目、模型和代码版本，避免大小不同的语料与不同候选预算导致结果不可比较。

### 7.3 最小指标与可复现输出

| 类别 | 必须记录 | 备注 |
|---|---|---|
| 检索质量 | NDCG@10、Recall@100、MRR 或适用指标 | 与任务粒度一致，候选重排不得使用全库 Recall 标签 |
| 多级商品相关性 | 按预注册 gain 映射计算 NDCG | 不将 Exact/Substitute/Complement 直接视为天然同等相关 |
| 时延 | P50 / P95、索引构建耗时 | 包含/排除哪些阶段须明示；区分预热与稳态 |
| 资源 | 索引磁盘、内存/显存、批处理规模、硬件 | 相同实验条件下对比 |
| 诊断 | 按 Query 类型分组、错误案例与候选阶段 Trace | 分析为什么提高或下降 |
| 复现 | 代码版本、Config、Data/Index Fingerprint、模型版本、Runfile | 第三方可重跑基本实验 |

质量结果应进行**同一 Query 集合上的配对比较**；有条件时报告 Bootstrap 置信区间，避免根据微小分差宣称算法优越。

### 7.4 最低消融矩阵

1. BM25 单路。
2. Dense 单路。
3. BM25 + Dense + RRF。
4. Hybrid + Cross-Encoder。
5. 在业务适配场景复用 Core，明确记录 Domain Schema / Aggregation / Relevance Profile 的不同。

可选：用理想候选 / 理想排序做 Oracle 诊断，估计召回与精排阶段的潜在改进上限。Oracle 仅用于分析，不进入实际部署。

## 8. V0 验收门槛（Definition of Done）

| 维度 | 通过条件 |
|---|---|
| 功能正确性 | 四种策略与两个 Domain Adapter 可重复运行；请求合法性、硬过滤、去重及错误情况通过测试。 |
| 数据一致性 | Entity↔Unit 映射可验证；固定快照重跑结果一致；旧修订不混入新快照。 |
| 评测正确性 | 全库检索和给定候选重排协议分开；Qrels 粒度与返回粒度一致；输出标准 Runfile / 报告。 |
| 算法证据 | 至少完成规定的四路消融与分场景错误分析；改进结论给出统计与成本上下文。 |
| Harness 能力 | 外部调用方可使用统一搜索契约而无需修改 Retrieval Core；Trace 能解释主要阶段。 |
| 成本透明度 | 报告时延、资源、硬件、索引构建时间，避免把离线编码开销藏在质量报告之外。 |
| 边界诚实 | README 明确“研究/工程原型、公开语料、无生产 ACL、无多模态上线”。 |

**不预设**必须超越某个公开 SOTA 的数值阈值。V0 的成功是建立可核查的正确基线；后续 V1 以基线为依据制定具体提升目标。

## 9. 阶段路线与修改边界

### V0：检索核心与证据链

完成数据适配、基线检索策略、统一 Search API、一次完整 BEIR 全库评测、一次完整 ESCI 给定候选重排评测，以及可复现 Trace / Runfile / README。采用固定公开语料和索引快照，允许全量索引重建。

### V1：业务适配与工程完整性

补足真实业务字段和属性过滤、Entity/Unit 聚合、索引更新删除的端到端一致性测试；构建**独立的商品全库检索评价协议**并公开其标注局限。若加入受限数据，必须另行实现和验证可信身份、授权和隔离机制。

### V2：按证据驱动的扩展

优先探索商品图文多模态检索；随后根据消融结果考虑 Query Routing、Late Interaction 和更复杂证据选择。每项新能力必须分别报告成本、收益、适用场景与对原能力的回归影响。

## 10. 开发前应决定但本版不冻结的事项

- [ ] 单后端技术验证：OpenSearch 或其他适合的成熟实现；比较本地可部署性与向量/稀疏/过滤能力。
- [ ] 具体模型：至少一个通用 Embedding 与一个 Cross-Encoder；注明语言与许可证适配。

- [ ] ESCI `product_locale` 及 E/S/C/I → 评价 gain 的任务定义。
- [ ] 统一硬件与延迟实验方案；确定是否有 CPU 回退或 GPU 批处理。
- [ ] 第一次发布的目录结构、CI 门槛与最小部署方式。

## 11. 已知风险与设计检查点

| 风险 | 检查方式 |
|---|---|
| “两个业务”其实只跑了两套不相干脚本 | 搜索核心不改动即可切换 Domain Adapter；差异在 Schema/Policy/Profile 层。 |
| 商品候选重排被包装成全库检索 | 报告必须分列任务协议；V0 README 显示业务验证边界。 |
| 文档级 Qrels 被用于直接评价 Passage | 固定 Unit→Entity 聚合并做自动化 ID 一致性测试。 |
| 混合召回高分来自不公平候选预算 | 固定 Top-N、总候选数及推理成本；报告有效候选覆盖。 |
| 增强方法只在反复调过的测试集有效 | 独立调参集、冻结配置、最终测试一次性报告。 |
| “企业级”沦为未验证的安全与可用性承诺 | 以可验证模块设计与研究原型表述；安全/HA 另立验收。 |
| 过度设计消耗时间，影响求职交付 | V0 只保留单后端、四策略、两适配器和两套评测协议。 |

## 12. 文档治理与变更规则

- **冻结**：第 0–9 节属于 V0.1 的规范性基线。Codex 可据此开展详细设计，但不得静默改变能力边界。
- **可细化**：模型、后端、字段序列化格式、实际代码结构、运行参数等非规范性细节可在后续实现设计中确定。
- **必要变更**：影响业务范围、数据关系、评测任务、授权边界或验收原则时，提交 ADR / RFC v0.2，写明理由、收益、代价和迁移影响。
- **变更记录**：`v0.1 · 2026-11-05 · 首次需求与架构基线冻结；包含 R-01 至 R-05 的实质修订。`
